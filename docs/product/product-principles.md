# 產品定位與設計原則

## 1. 產品定位

Jianghu 是一款融合武俠／江湖元素的遊戲化自我管理 Web App。

核心不是製作完整 RPG，而是以武俠風格包裝個人成長與任務管理，降低開始與持續現實任務的阻力，協助使用者：

- 持續完成現實任務。
- 建立學習、運動、自律等生活習慣。
- 降低短影音等高刺激內容對日常行動的干擾。
- 記錄行動並查看長期累積成果。
- 透過適度的視覺與主題包裝，提高持續使用與持續行動的意願。

對外定位優先描述為：

> **武俠風個人成長與任務管理工具。**

而不是 RPG、Web Game 或完整角色扮演遊戲。

## 2. 成功指標

不以 App 停留時間作為核心成功指標。

更有意義的觀察方向包括：

- 每週有效技能鍛鍊時間。
- 任務開始率與完成率。
- LeetCode 練習量。
- 專案開發時數。
- 運動次數。
- 防沉迷目標達成情況。

完成必要操作後快速回到現實，對本產品而言可以是健康的 UX。

## 3. 品牌方向

目前品牌方向：

```text
產品品牌：江湖修行錄
產品定位：個人成長與任務管理
視覺／主題風格：武俠
```

「江湖」代表產品世界觀與包容性，可容納學習、工作、運動、自律、社交與生活成長。

「武俠」主要作為產品風格描述，不應讓產品被理解為完整 RPG。

## 4. 核心產品原則

### 4.1 現實行動優先

最高層判斷標準不是「遊戲區是否更好玩」，而是：

> 打開 App 後，是否真的更容易開始或推進現實工作。

目前方向偏向：

```text
現實任務
→ 真實紀錄
→ 武學修為／遊戲回饋
```

不應讓遊戲需求反向要求使用者為了取得某種遊戲資源而建立特定現實任務。

### 4.2 遊戲化應改善做事體驗

比起持續擴張獨立遊戲區，更應優先改善：

```text
Planning
→ Execution
→ Progress
→ Reflection
```

武學區維持收藏、修煉、突破等輕量 meta-progression。

### 4.3 真實紀錄的價值高於虛擬 Reward

虛擬修為與武學進度是激勵層；真正長期有價值的是：

- Task Activity。
- TaskCycle。
- 實際投入與完成紀錄。
- Reflection。
- 可回顧的個人修行史。

數值描述行為進度，不評判人的價值。

### 4.4 高頻操作低摩擦

建立、開始、更新與完成任務屬高頻操作，應盡量簡單。

最低使用路徑應保持為：

```text
建立／選擇任務
→ 執行／記錄進度
→ 完成
```

使用者即使完全不進入武學、探索或圖鑑介面，Task 與 History 仍應完整可用。

### 4.5 不建立現實生活的許可制度

遊戲層可以獎勵現實行動，但不應規定完成任務後才有資格休息、娛樂、購物等現實權利。

### 4.6 降低作弊價值，而不是建立重度 Anti-Cheat

目前主要使用情境是自用。系統不需要試圖完全防止使用者修改紀錄、程式或資料庫。

設計重點是讓誠實紀錄本身具有長期價值。若未來加入 evidence / provenance，應以 optional 為主，不應為防作弊增加大量操作摩擦。

### 4.7 避免遊戲機制扭曲真實行為

不得因 Reward 設計鼓勵：

- 把一件事情拆成大量小任務 farming。
- 故意中斷後再重啟以刷永久能力值。
- 為了遊戲資源增加不必要的現實行為。

子任務不應獨立產生 Reward；Reward 應更關注 difficulty、importance 與實際 completion progress，而不是 task count。

### 4.8 避免 App 成為新的 distraction

完成現實任務後的遊戲操作應短而有感，避免使用者花大量時間逛市集、整理庫存或操作複雜經濟。

## 5. V1 Scope Guardrails

V1 優先成為可每天使用的「武俠風任務與修行紀錄 App」。

核心方向包括：

- 任務池。
- 今日任務。
- 可選今日主線。
- 一般／計數／計時任務。
- 進度與 Activity History。
- 簡單武學養成與收藏。

V1 不應優先建立：

- 一般物品／裝備／消耗品／強化／合成。
- 通用 Item / Inventory Domain。
- 銀幣、一般商店與複雜市場。
- 完整城市與大地圖。
- 自宅。
- 完整門派 membership／退派／轉派／忠誠度。
- 社交與重度敘事。
- AI 師傅或以 AI 驅動核心 Reward。
- 自創武學；此項屬長期 endgame。

新增資源、素材或貨幣前，必須先確認它是否真的產生新的決策價值，而不是只增加 source / sink 與平衡成本。

## 6. 開發 Scope Guardrail

開發期間出現的新點子先記錄到 Backlog，不立即中斷目前 Sprint／當日目標。

核心原則：

> 如果產品設計開始持續延後可用版本，應停止擴張並回到目前可落地的核心功能。
