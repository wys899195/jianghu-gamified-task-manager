# TypeScript 註解規範

本文件整理目前專案 `.ts` 檔案已使用的註解風格，作為未來 Backend、Frontend TypeScript 與 TSX 檔案新增或修改註解時的共同規範。

## 1. 註解原則

- 註解應補充程式碼無法直接表達的責任、流程、原因、限制或預期行為。
- 優先讓命名、型別與程式結構表達「做什麼」，註解補充「為什麼」及重要的行為邊界。
- 註解必須與實作同步；修改流程、API、錯誤處理或安全性行為時，同步檢查鄰近註解。
- 使用繁體中文描述專案規則與業務語意；既有技術名詞、API 名稱、類別名稱、函式名稱與欄位名稱保留英文。
- 註解使用完整句子，中文敘述原則上以全形句號 `。` 結尾。
- 不為每一行程式碼加註解，也不重複翻譯變數名稱或明顯的控制流程。

## 2. 註解類型與使用時機

### 2.1 檔案開頭責任說明

當檔案具有明確的模組責任、啟動責任或跨層邊界時，在 import 前使用檔案說明。現行專案使用等寬分隔線包住說明文字：

```ts
// ========================================
// <檔案主要責任或功能名稱>
// <補充說明該檔案負責的功能、業務邏輯或跨層邊界>
// ========================================
```


規則：

- 第一行與最後一行使用 `// ========================================`。
- 中間先說明檔案的主要責任，再補充包含的範圍或重要邊界。
- 說明以一至三行為原則，不列出每個 export。
- 純型別、簡單測試資料或內容已由檔名充分表達的檔案，不必為了形式強行加入檔案標頭。

### 2.2 主要區段標題

檔案內包含多個可獨立理解的功能或業務邏輯時，用分隔線切分同層級區段。每個區段代表一項具名責任；區段標題下的常數、型別、輔助函式與主要函式，都應服務於該責任，直到下一個同層級區段標題開始。

```ts
// ========================================
// <功能或業務邏輯名稱>
// ========================================
```

規則：

- 只用於可獨立理解的功能或業務邏輯，不用於每個小步驟。
- 標題應簡短且具體，描述該區段的功能或業務責任；可沿用專案既有的英文功能名稱或常用技術名稱。
- 分隔線長度固定為 `========================================`。
- 區段標題前後維持空行，讓程式區塊容易掃讀。
- 不將同一項業務邏輯拆散到不相關區段；若區段內容已無法由單一責任概括，應重新拆分程式結構或調整區段邊界。

### 2.3 函式、方法與型別的 JSDoc

對外 export 的函式、重要 middleware、Service 流程、Repository 操作及需要解釋語意的型別，使用 `/** ... */` JSDoc。第一段先說明責任，必要時再用標題、條列或流程描述細節：

```ts
/**
 * 執行功能所需的主要業務流程。
 *
 * 流程：
 *
 * 1. 驗證輸入資料
 * 2. 取得所需資料
 * 3. 套用業務規則
 * 4. 儲存處理結果
 */
export async function executeFeature(
    request: FeatureRequest,
): Promise<FeatureResult> {
```

規則：

- 第一行使用動詞或簡潔名詞說明責任，例如「驗證輸入資料並建立處理結果。」。
- 需要說明多個有順序的步驟時，使用 `流程：` 加上從 `1.` 開始的編號清單。
- 需要說明多個並列條件、限制或責任時，使用簡短標題加 `-` 條列。
- API route 的 JSDoc 可包含 HTTP method、path、Request、Response、Cookie 或重要的 middleware 邊界。
- 只有在參數、回傳值或例外行為不易由型別與命名推斷時，才補充 `@param`、`@returns` 或 `@throws`；不為形式而增加空泛標籤。
- JSDoc 應描述目前實作的公開契約，不在註解中記錄尚未實作的未來設計。

### 2.4 函式內行註解

當某段程式碼的原因、資料流或安全性限制不是從程式碼本身立即可見時，使用單行 `//` 註解：

```ts
// 原始值僅在本次流程中使用；
// 持久化時只儲存轉換後的安全值。
const persistedValue = transformSensitiveValue(rawValue);
```

適合說明：

- 安全性或敏感資料處理，例如密碼、Token、Cookie 與 Hash。
- 跨層資料傳遞原因，例如為何要使用驗證後的資料覆寫 request body。
- 非直覺的錯誤處理、冪等行為或相容性限制。
- 一個具名步驟的開始，例如「取得相依資料」或「套用業務規則」。

避免寫成只重複程式碼的註解：

```ts
// 錯誤：呼叫儲存函式。
const result = await saveRecord(input);
```

## 3. 格式與文字規則

- 單行註解使用 `// `，註解文字與斜線之間保留一個空格。
- 多行 JSDoc 使用 `/**` 開始、`*/` 結束，每一行內容以 ` * ` 開頭。
- `流程：`、`Request:`、`Response:`、`前置條件：` 等標題後保留空行，再列出內容。
- 條列項目使用 `- `；有先後順序的步驟使用 `1. `、`2. ` 等編號。
- 專有名詞與程式識別字依現有專案慣例保留，例如模組名稱、類別名稱、函式名稱、欄位名稱與既有技術術語。
- 註解內容不放入密碼、Token、API key、私密設定值、真實個資或其他敏感資訊。

## 4. 不使用註解的情況

- 不為單純的 assignment、return、if 判斷或函式呼叫逐行翻譯程式碼。
- 不用註解掩蓋不清楚的命名；若名稱本身不足以表達責任，優先改善命名或拆分函式。
- 不保留已失效的流程、API path、欄位名稱或架構描述。
- 不使用註解作為暫存的 TODO 清單；若需要追蹤待辦，應使用專案既有的需求、Issue 或工作流程。
- 不為了與其他檔案數量一致，在沒有額外資訊時加入空泛的檔案標頭。

## 5. 新增或修改 TypeScript 檔案的檢查清單

- [ ] 檔案是否需要說明模組責任？若需要，是否放在 import 前？
- [ ] 主要流程是否以區段標題清楚分隔？
- [ ] export 的函式、middleware、Repository 操作或重要型別是否需要 JSDoc？
- [ ] 註解是否補充原因、限制、資料流或安全性，而非重複程式碼？
- [ ] 流程步驟是否使用 `流程：` 與編號清單？並列條件是否使用 `-` 條列？
- [ ] 註解中的 API、欄位、錯誤代碼與實作是否一致？
- [ ] 是否沒有放入敏感資訊或已過期的設計描述？

## 6. 適用範圍

本文件適用於 Backend／Frontend 的 `.ts` 與 `.tsx` 原始碼。TSX 需要註解時沿用本文件的責任、原因與行為邊界原則，並避免為每個 JSX element 逐行加註解。

本文件不涵蓋 `.sh`、`.env`、`.json`、`.yaml` 或 `.gitignore` 的格式註解。Backend 單元測試的 testcase block comment、AAA 區塊標記、fixture／Mock 註解與 `describe` 命名，依 [Backend Unit Testing](../../testing/backend-unit-testing.md) 執行；通用檔名與型別規則見 [`../coding-style.md`](../coding-style.md)。
