# Frontend Unit Testing

本文件規範 Frontend 的單元測試。Frontend 目前尚未建立可執行的測試框架或測試檔；因此本文件定義測試工作開始前的判斷與完成後必須遵循的原則，不指定未導入的函式庫、mock API 或目錄結構。

## 工具鏈與執行

- 新增、修改元件測試前，先檢查 `Frontend/package.json`、既有測試檔與設定，確認目前的測試框架、執行指令、命名與目錄慣例。
- 不可在單一元件測試工作中自行新增、替換或切換測試框架；若尚無工具鏈，先指出缺口並取得建立測試架構的明確需求。
- 測試修改後，執行 Frontend 已設定的測試與型別檢查命令；沒有既定命令時，不臆測或自行建立替代命令。

## 案例設計與 Arrange / Act / Assert

- 優先測試使用者可觀察的行為：畫面狀態、輸入、事件、錯誤訊息與非同步結果。
- 高優先情境為表單驗證、登入狀態、權限、路由保護與非同步 UI 狀態；不為純呈現或第三方元件內部行為追求覆蓋率。
- 每個案例只驗證一個正常、已定義錯誤或關鍵邊界情境。先確認測試目標、輸入、需要控制的邊界與預期畫面／互動結果；未確認需求不可寫成規格。
- 依 Arrange / Act / Assert 排列：準備 props、fixture 與 mock；實際 render 並觸發互動；驗證使用者可觀察結果。區塊之間保留空行。
- 測試失敗時，先確認規格、實作與測試期待何者不一致；不要只為通過測試修改預期結果。

## Mock 與測試對象

- 實際 render 被測元件；不要 mock 元件本身。
- mock API client、router、瀏覽器 API、時間與其他外部邊界，讓測試不依賴網路、後端服務或不可控環境。
- 純格式化、轉換與計算邏輯優先以真實實作和 fixture 測試；避免為無副作用依賴增加 mock。
- fixture 只放可重用輸入與預期資料，不放測試流程。實際命名與位置待 Frontend 工具鏈建立後，以既有慣例為準。

## 名稱、註解與維護

- 遵循 Frontend 已建立的 TypeScript、測試檔命名與目錄規則；不使用 `any`。
- 每個測試須使用既有框架的案例 API，名稱描述可觀察行為與結果，並沿用 Backend 已確認的註解意圖：在測試案例上方說明測試目標與預期結果。實際 comment 格式以未來建立的 Frontend 慣例為準。
- 保持案例獨立，不依賴測試執行順序；每個案例自行設定所需狀態與 mock。
- 若 Frontend 新慣例與本文件原則衝突，先檢查並指出差異，不自行建立另一套規則。
